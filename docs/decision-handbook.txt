SkyPoints Decision Log

This file confirms accepted design decisions.

Decision: Complete write flow
Confirmation: Read the daily member flat file and redemption JSON file from local input directories. Write Raw Delta, Staging Delta, Target Delta, and export files.

Decision: Processing platform
Confirmation: Use Docker, Apache Spark, and Delta Lake. Do not use Snowflake or MinIO.

Decision: Local storage
Confirmation: Mount the host data/ directory in both Spark containers at /opt/skypoints-data/. Use local file:/// Delta paths.

Decision: Country targets
Confirmation: Store members in one partitioned Delta target by country_code. Do not create physical country tables dynamically.

Decision: Country outputs
Confirmation: Produce country-specific views or export files from the target Delta table.

Add new accepted decisions to this log ----

Decision: Generate Sample files using Agent
Confirmation: Use AI Agent to defer work of generating sample records to be ingested - Generated txt files using Agent and JSON files for redemption

Decision: Raw layer Control table: source_path and ingestion time - we will use this to filter out those records that have already been ingested

Decision: Control table lookup scale
Confirmation: Collect only processed source paths from the control table. The table stores one row per file, not one row per source record.

Decision: Raw layer schema - we will use a simple schema with the following fields: source_path, raw_record, and ingestion_time and then split the raw_record on pipe to get the individual fields for the staging layer

Decision: Staging layer schema - we will use a schema with the following fields: member_id, first_name, last_name, email, country_code, and ingestion_time. We will also add a partition column for country_code to optimize queries.

Decision: Target Layer - we will create a consolidated target layer with the latest member records for member_id and then we can create country-specific views or export files from this target layer. We will use Delta Lake's MERGE operation to update the target layer with new records from the staging layer.

Decision: Exports Layer - additional country files confused me a lot initially, so what I could come up with was a stable exports layer - Country specific tables go in the exports folder as well as the files that have been exported - Each country that we know have a export function associated with - so as and when required - we can add a new export function for a new country that we want to track and run the script back - we will get those records loaded - Now, this can be an issue - becuase records are in billions - so A better architecture would be a view on top of the target table layer - Then we can also just simply define the views as DDL statments and our exports script would be limited to defining country specific exports layer

Decision: using Pandas - using Pandas for exporting the data to CSV files and Excel files - so as to stabilize on the file output naming conventions. Using Spark to export CSVs and Excel would be a bit of a pain - so we will use Pandas for this - and we will use Spark to read the data from the target layer and then convert it to Pandas and then export it to CSVs and Excel files

Decision: Philippines Export: I didn't assume a Philippines file export without an output template. Keep Philippines data in the country-partitioned Delta target until we have a clear sample export

Decision: Redemtpion Layer - simply read the redemption file - rank the records locally and then on the target table itself - we can get a flattened table finally in the target layer - which can then be directly used to query the data and write sqls and stuff

Major Decision: Why Delta Lake - because for quick turnarounds and fast and stable movability - delta lakes are great and otherwise also they are great to work with and very easy as there are no warehouse mounting issues and etc.
Other way we could have worked on this will be to setup a spark.sql.catalog.spark_default - and setup a local file based warehouse - then we could have easily see the local data and query local data as well

Why Spark on Docker Compose - Simply because - easy to reproduce - I have already worked on this kind of stuff - so my familiarity with the setup and the ease of use - I can easily setup a spark cluster on my local machine and then run the code and test it - Also, I can easily share the docker-compose file with others and they can easily run the same setup on their local machines as well

Decision: Validate mandatory fields, data formats, dates, and key uniqueness. Quarantine invalid records before staging and target writes.

Decision: Data Validation Tests
Use Spark tests to verify validation rules fire at runtime and failed records reach the quarantine layer. Run `make spark-test-validations` to verify the behavior.
